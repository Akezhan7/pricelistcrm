# Панель задач для сотрудников

## Цель

Сделать отдельный модуль CRM для универсальных внутренних задач сотрудников. Задачи не являются частью очереди товаров: очередь управляет жизненным циклом карточек товара, а новый модуль покрывает любые поручения руководителя.

## Этап 1. Рабочее ядро задач

Полноценная первая версия, которую можно проверять с клиентом.

- Только администратор создает задачи.
- Задача назначается одному активному сотруднику.
- Сотрудник видит свои задачи.
- Администратор видит все задачи.
- Поддерживаются статусы: `Новая`, `В работе`, `На проверке`, `Возвращена`, `Выполнена`, `Отменена`.
- Сотрудник может начать задачу и отправить ее на проверку.
- Администратор может принять задачу, вернуть на доработку или отменить.
- В задаче есть название, описание, ответственный, приоритет и срок.
- Ведется история действий: создание, смена статуса, принятие, возврат, отмена.
- В интерфейсе появляется страница `Задачи` с фильтрами, списком, созданием и просмотром деталей задачи.
- Очередь товаров и `CollectorTask` не изменяются.

### Критерии готовности этапа 1

- Администратор создает задачу сотруднику.
- Сотрудник видит назначенную задачу в своем списке.
- Сотрудник переводит задачу в работу и отправляет на проверку.
- Администратор принимает или возвращает задачу.
- История задачи показывает, кто и когда выполнил ключевые действия.
- Фильтры по статусу и ответственному работают без изменения продуктовой очереди.

## Этап 2. Удобство управления

Улучшения после проверки базового процесса.

- Редактирование задачи администратором.
- Переназначение ответственного.
- Комментарии в задаче отдельным обсуждением.
- Поиск по названию и описанию.
- Фильтр просроченных задач.
- Счетчики задач по статусам.
- Вкладки `Мои`, `Поставленные мной`, `Все`.

## Этап 3. Расширения

Только если клиент подтвердит необходимость.

- Опциональная ссылка задачи на товар, поставщика, заявку или заказ.
- Внутренние уведомления CRM.
- Вложения к задачам.
- Повторяющиеся задачи.
- Аналитика по сотрудникам.
- Канбан-вид.

## Рекомендуемый порядок

Сначала реализовать и проверить этап 1 как самостоятельный модуль. После приемки переходить к этапу 2, чтобы улучшать реальный сценарий использования, а не заранее усложнять систему.
