# Product Lifecycle CRM Roadmap Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Поэтапно доработать текущую CRM `crm3` под ТЗ PKS Group: единая карточка товара, жизненный цикл товара, роли, очереди задач, история, файлы, маркетплейсы, склад, KPI и Казпатент.

**Architecture:** Не переписывать систему с нуля. Расширять существующую модель `Product` и связанные модули, добавляя lifecycle как отдельный слой поверх текущих товаров, поставщиков, закупок и склада. Каждый этап перед реализацией начинается с анализа текущего кода и согласования решения с владельцем проекта.

**Tech Stack:** React 19 + TypeScript, TailwindCSS, Express, Sequelize, PostgreSQL, JWT, Multer, существующая структура `client/` и `server/`.

## Основной Принцип Работы

Этот roadmap не является разрешением сразу реализовывать все подряд.

Перед каждым этапом обязательно:

- [ ] Изучить текущий код именно по теме этапа.
- [ ] Сформулировать лучшее техническое решение.
- [ ] Описать затрагиваемые модели, API, UI, миграции и риски.
- [ ] Получить подтверждение владельца проекта.
- [ ] Только после подтверждения писать код.
- [ ] После реализации проверить этап и зафиксировать результат.

Запрещено:

- временные поля "на потом разберемся";
- обходные CSS/JS-костыли вместо нормальной модели;
- дублировать одну и ту же бизнес-логику на frontend и backend без источника правды;
- добавлять роль или статус только в UI без backend-проверки;
- ломать существующие товары, поставщиков, заявки, склад и прайс-лист;
- создавать чрезмерное количество мелких тестов на каждую кнопку;
- какие либо временные костыли в проекте.

Разрешено и ожидается:

- маленькие, законченные релизы;
- миграции с обратной совместимостью;
- backend-валидация критичных правил;
- UI, который помогает сотруднику делать одно понятное действие;
- тесты после важных бизнес-изменений, а не после каждого косметического штриха.

## Что Хочет Клиент

Клиент хочет превратить текущую CRM из системы товаров, поставщиков, закупок и склада в операционную систему запуска товара.

Ключевая идея из ТЗ:

> Каждый товар создается один раз. Все сотрудники работают с одной карточкой товара, дополняя ее своей информацией на своем этапе.

Нужный жизненный цикл:

1. Новые товары.
2. Передан дизайнеру.
3. Карточка создана.
4. Проверка карточки.
5. Размещение на маркетплейсах.
6. Закуп.
7. Склад.
8. В продаже.

Роли по ТЗ:

- Анас / руководитель проекта: создание новых товаров, назначение дизайнеру, проверка, KPI-вес, общий контроль, по сути он и есть админ.
- Нурхан / Алиша: фото, JPG-слайды, PSD, исправление доработок.
- Улшат / Гульнур: маркетплейсы, описание, цена продажи, Kaspi SKU, реклама, акции.
- Ерман: закуп и подтверждение поступления.
- Учетчик: складской адрес, вес, габариты, уточнение себестоимости.
- Администратор: пользователи, права, справочники, настройки.

MVP из ТЗ:

- карточка товара;
- пул новых товаров;
- назначение дизайнера;
- загрузка фото/JPG/PSD;
- проверка и доработка с комментарием и файлом;
- размещение на Kaspi;
- закуп;
- склад;
- в продаже;
- права доступа;
- история действий;
- вес карточки для KPI;
- блок Казпатента;
- блок маркетплейсов с возможностью расширения.

Будущие функции:

- рисование поверх изображения;
- интеграции Kaspi / ProfitBot;
- автообновление остатков и цен;
- расширенные отчеты KPI и зарплаты;
- массовая регистрация Казпатента через пакеты;
- импорт/экспорт Excel;
- Telegram или внутренние уведомления.

## Текущее Состояние CRM

Уже есть полезная база:

- `server/models/Product.js` - товар с названием, артикулом, себестоимостью, продажной ценой, фото, Kaspi-полями, остатками и категорией.
- `server/models/Supplier.js` - поставщики.
- `server/models/ProductSupplier.js` - связь товар-поставщик.
- `server/models/ProductVariation.js` - вариации товара.
- `server/models/Order.js` - закупочные/возвратные заявки.
- `server/models/OrderStatusHistory.js` - история статусов заявок.
- `server/models/PriceHistory.js` - история цен.
- `server/models/StockHistory.js` - история остатков.
- `server/models/WarehouseReceipt.js` и `WarehouseReceiptItem.js` - приемка склада.
- `server/models/User.js` - пользователи и роли.
- `client/src/pages/ProductsPage.tsx` - страница товаров.
- `client/src/components/CreateProductModal.tsx` - создание товара.
- `client/src/components/EditProductModal.tsx` - редактирование товара.
- `client/src/pages/Orders.tsx` и `OrderDetails.tsx` - заявки.
- `client/src/pages/WarehouseReceipt.tsx` - приемка.
- `client/src/pages/Users.tsx` - пользователи.

Главный разрыв с ТЗ:

Текущая CRM работает как справочник товаров, поставщиков, закупок и склада. ТЗ требует workflow-систему, где товар сам является задачей и проходит по ответственным сотрудникам.

- текущую загрузку файлов;
- текущие UI-страницы товаров и поставщиков;

**Решения, которые нужно принять:**

**Цель:** Добавить товару жизненный цикл на backend-уровне без сложного UI.

**Что реализовать после согласования:**

- текущий этап товара;
- назначенный ответственный;
- назначенный дизайнер;
- базовые переходы между этапами;
- миграцию существующих товаров;
- backend-валидацию допустимых переходов.

**Предварительная модель статусов:**

- `new`

- `content_created`
- `review`

### Этап 4: Личные Очереди Сотрудников

**Цель:** Каждый пользователь должен видеть свою очередь задач, а руководитель - общую картину.

Очередь должна считаться backend-ом по роли, ответственному и этапу. UI не должен самостоятельно решать, какие задачи кому положены.

### Этап 5: Контент Карточки - Фото, JPG, PSD И Файлы

**Цель:** Дать дизайнеру нормальный блок загрузки и хранения материалов карточки.

**Что реализовать после согласования:**

- отдельную сущность файлов товара;
- типы файлов: product_photo, slide_jpg, psd_source, revision_attachment, patent_file, other;
- несколько фото;
- несколько JPG-слайдов;
- PSD-исходник;
- дополнительные файлы;
- автора загрузки;
- дату загрузки;
- безопасные ограничения MIME-типов и размеров.

**Почему отдельная сущность лучше:**

Сейчас у товара есть одно поле `image`. ТЗ требует много файлов разных типов. Расширять это через `image2`, `image3`, `psdFile`, `slide1` нельзя: это быстро сломает модель.

**Вероятные backend-файлы:**

- создать `server/models/ProductAsset.js`;
- изменить `server/models/associations.js`;
- создать миграцию;
- изменить или расширить `server/middleware/upload.js`;
- создать routes/controller для файлов товара.

**Вероятные frontend-файлы:**

- `client/src/types/index.ts`
- новый `client/src/components/ProductAssetsPanel.tsx`
- страница карточки товара или workflow-страница.

**Проверка:**

- дизайнер загружает фото;
- дизайнер загружает JPG;
- дизайнер загружает PSD;
- неправильный файл отклоняется;
- файлы видны в паспорте товара.

**Тесты:**

- backend-проверка разрешенных и запрещенных типов;
- ручная проверка загрузки через UI.

## Стратегия Тестирования

Не переусердствовать с тестами.

Тестировать обязательно:

- миграции БД;
- lifecycle-переходы;
- запрет неправильных переходов;
- права доступа;
- загрузку файлов;
- изменение цены/себестоимости;
- расчет KPI;
- ключевой end-to-end сценарий.

Не нужно тестировать отдельно:

- каждую маленькую кнопку;
- каждый CSS-класс;
- каждую подпись;
- однотипные поля формы, если они уже покрыты общей проверкой формы.

Рекомендуемый ритм:

- после архитектурного этапа: согласование без тестов;
- после backend-этапа: минимальные API/integration проверки;
- после UI-этапа: сборка + ручной сценарий;
