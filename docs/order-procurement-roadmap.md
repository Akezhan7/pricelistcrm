# Roadmap: создание и статусы заявок на закупку

## Цель

Сделать работу с заявками быстрее на раннем этапе заполнения CRM, сохранив корректность складского учета, задолженности и истории операций.

## Этап 1. Товары до поставщика и черновик без поставщика

Статус: реализован.

### Пользовательский сценарий

- Каталог всех активных товаров доступен сразу после открытия формы заявки.
- Пользователь может найти и добавить товары до выбора поставщика.
- По выбранным товарам CRM показывает связанных поставщиков и приоритетно предлагает тех, которые покрывают больше позиций.
- Пользователь может выбрать любого активного поставщика, даже если часть товаров с ним еще не связана.
- Закупку можно сохранить без поставщика как черновик в статусе `Создана`.
- Возврат без поставщика создать нельзя.
- В существующий черновик поставщика можно назначить позднее через редактирование заявки.
- Смена или удаление поставщика в форме не удаляет уже выбранные товары и не перезаписывает введенные цены.

### Ограничения и целостность данных

- У черновика без поставщика недоступны отправка, подтверждение, оплата и смена рабочего статуса.
- Сервер повторно проверяет это ограничение независимо от интерфейса.
- Финансовая задолженность не рассчитывается для заявки без поставщика.
- Привязка товара к поставщику не создается автоматически: справочник меняется только отдельным явным действием пользователя.
- Существующие заявки с поставщиками продолжают работать без изменения сценария.

### Технические изменения

- Сделать `orders.supplier_id` nullable с обратимой миграцией.
- Обновить модель, API создания и редактирования заявки, типы клиента и отображение отсутствующего поставщика.
- Добавить загрузку общего каталога и расчет рекомендаций поставщиков в форме создания.
- Добавить выбор поставщика в редактирование черновика.
- Добавить серверную защиту операций, требующих поставщика.

### Критерии готовности

- Товар можно добавить в новую закупку без предварительного выбора поставщика.
- Закупка без поставщика сохраняется и отображается как `Без поставщика`.
- Поставщика можно назначить позднее, после чего обычный процесс становится доступен.
- Возврат без поставщика отклоняется.
- Попытка изменить статус или зарегистрировать оплату без поставщика отклоняется сервером.
- Старые заявки и черновики из панели поставщика продолжают работать.

## Этап 2. Быстрые безопасные статусы, отмена и задолженность

Статус: реализован.

### Пользовательский сценарий

- Администратор и менеджер закупок могут пропускать необязательные информационные этапы без последовательного сохранения каждого статуса.
- Допустимые переходы приходят с сервера и не дублируются отдельной таблицей на клиенте.
- Статус `Принята на складе` устанавливается только через полноценную складскую приемку.
- Для быстрого завершения доступно действие `Принять на склад`, которое открывает форму фактической приемки из любого разрешенного рабочего этапа.
- `Закрыта` означает завершенную закупку и не удаляет заявку.
- Добавляется отдельный статус `Отменена` для несостоявшейся закупки.
- Перед закрытием неоплаченной заявки CRM предупреждает, что остаток сохранится в задолженности.

### Финансовые правила

- В задолженность входят только фактически принятые и закрытые закупки.
- Черновые, рабочие и отмененные заявки не создают долг поставщику.
- Оплата и операционный статус остаются разными характеристиками заявки.
- Отмена сохраняет заявку и историю, но исключает ее из задолженности.

### Технические изменения

- Централизовать каталог статусов, переходы и ролевые ограничения на сервере.
- Добавить статус `Отменена` в БД, API, типы, фильтры и историю.
- Исключить прямую текстовую установку складского статуса в обход приемки.
- Скорректировать расчет задолженности и статистику заявок.
- Добавить подтверждения для закрытия и отмены с понятным описанием последствий.

### Критерии готовности

- Информационные этапы можно безопасно пропустить одним изменением.
- Приемка всегда обновляет остатки и создает складскую историю.
- Закрытая неоплаченная закупка остается видимой и учитывается как долг.
- Отмененная закупка остается в истории и не учитывается как долг.
- Клиент и сервер используют единые правила доступных переходов.

## Порядок проверки

- Для каждого этапа: целевые тесты бизнес-правил и измененных API-контрактов.
- Проверка типов клиента и серверного синтаксиса.
- Точечная ручная проверка основного пользовательского сценария.
- Полная сборка клиента выполняется после завершения каждого этапа, а не после каждого локального изменения.
