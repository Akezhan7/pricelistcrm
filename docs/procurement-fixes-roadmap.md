# Roadmap: поиск, закупки и согласованность очереди

Дата: 08.09.2026. Статус: этапы 1-4 реализованы локально; проверка конкретных production-карточек ожидает развёртывания.

Цель: исправить поиск и зависание товаров, добавить чеки и разрешить обоснованные корректировки закупок без потери истории, остатков и расчётов с поставщиками.

## Основания и границы

- План составлен по текущему коду и сообщениям клиента. Данные конкретных проблемных заявок на production не исследованы; причины повреждённых связей требуют подтверждения по их ID.
- Подтверждено: `EditOrderModal.tsx` загружает только 1000 активных товаров, затем ищет локально по `name` и `article`. Аналогичная ограниченная загрузка осталась в `CreateOrderModal.tsx`. Старые товары могут не попадать в загруженную выборку независимо от привязки к поставщику.
- На странице товаров уже используется серверный поиск с пагинацией. Жалобу на отсутствие товаров именно там проверить отдельно: текущие фильтры, активность товара, ответ API и версию production. Не объявлять все случаи одной ошибкой и не пересоздавать товары.
- Чеки частично реализованы: есть `Payment.receiptUrl`, загрузчик `uploadReceipt` и передача файла через `paymentsApi`. Однако оплата из `OrderDetails` через `PaymentModal` и `orderController.updatePayment` эту возможность не использует.
- В `orderController.updateOrder` редактирование ограничено четырьмя ранними статусами. `deleteOrder` разрешает мягкое удаление только созданной неоплаченной заявки. `orderItemSyncService` отдельно запрещает удалять и заменять строки, связанные с lifecycle.
- В запуске продаж интерфейс считает запуск завершённым по любой из двух дат (`flags.completedAt || product.lifecycleCompletedAt`), а сервер требует обе. Количество включённых рекламных флагов сервер не ограничивает. Несогласованность условий подтверждена; конкретное состояние товара нужно проверить.
- Обычная приёмка обновляет очередь только при найденной связи `ProductLifecyclePurchase.orderItemId`. Приёмка из очереди проверяет статус заявки и создаёт отдельное поступление. Для групповой заявки этот путь также выставляет статус всей заявки после обработки одного товара. Эти пути необходимо согласовать.
- Личный кабинет поставщика, новый бухгалтерский модуль и полный редизайн не входят в задачу. Пункты клиента 3 и 4 объединены в один этап корректировок.

## Этап 1. Поиск товаров и сохранение рекламы

Замечания клиента: 1 и 5.

### Поиск

- [x] Перевести выбор товаров в редактировании и создании заявки на существующий серверный поиск каталога. Использовать текущие правила поиска по названиям и артикулам, включая внутреннее название и поля Kaspi; не дублировать локальный поиск по неполной выборке.
- [x] Добавить debounce около 300 мс, защиту от устаревших ответов и доступ к следующим страницам результатов. Не заменять `limit=1000` другим большим лимитом.
- [x] Сохранить добавленные строки и введённые цены/количества при смене запроса и страниц. Не загружать всю базу для восстановления уже выбранных товаров.
- [x] Выбранный поставщик определяет подсказку закупочной цены, но не должен незаметно исключать подходящий товар. Сохранить действующие правила добавления и выбора цены; проверку конкретных production-связей выполнить после развёртывания.
- [ ] Для отсутствующего товара в основном каталоге сопоставить запись по ID/артикулу, активность, фильтры, API и production-версию. Исправлять только подтверждённую причину; не активировать архивные товары автоматически.

### Реклама

- [x] Согласовать определение завершённого запуска в `ProductSaleLaunchPanel`, сервисе и контроллере запуска продаж. При расхождении дат последующее сохранение восстанавливает недостающую дату.
- [ ] Проверить товар со скриншота и происхождение расхождения дат после развёртывания. Локально реализовано безопасное восстановление отсутствующей записи/даты настроек по уже завершённому lifecycle.
- [x] Разрешить любой набор рекламных флагов: один, несколько, все или ни одного. Завершение запуска является отдельным действием, наличие всех галочек не требуется.
- [x] Сохранять историю изменений и русские сообщения об ошибках; не ослаблять права доступа и обязательные условия этапа.

Готовность: старый товар за пределами первой тысячи находится по названию и артикулу и добавляется в заявку; многопоставщицкие товары не теряются при пагинации. Единственная выбранная рекламная активность сохраняется после повторного открытия; корректно обрабатываются обе комбинации отсутствующей даты.

Проверка: точечные проверки поиска на каталоге больше 1000 товаров, гонки ответов и сохранения строк; тесты правил запуска и один браузерный сценарий каждого окна. Основные места: `EditOrderModal.tsx`, `CreateOrderModal.tsx`, существующий поиск `productController`, `ProductSaleLaunchPanel.tsx`, `productSaleLaunchService.js`.

## Этап 2. Приёмка и движение товара по очереди

Замечание клиента: 6. Выполнить до расширения редактирования заявок.

- [ ] Разобрать конкретный застрявший товар: заявка, её строка, закупочный лист, lifecycle-закуп, документы приёмки, фактически принятое количество и история статусов. Отдельно проверить ручное добавление товара и добавление через очередь.
- [x] Согласовать оба пути приёмки на уровне существующей складской операции. Из очереди открывать приёмку связанной заявки с нужной строкой; не создавать независимое повторное поступление для уже принятой партии.
- [x] Для групповых заявок определять результат по строкам и принятому количеству. Приёмка одного товара не должна автоматически объявлять остальные принятыми. Проверить существующее значение приёмки с расхождениями: это может быть окончательная поставка меньшего количества, а не ожидание второй партии.
- [x] Обеспечить сохранение связи первичного закупа с конкретной строкой заявки при создании из листа и редактировании. Не связывать любой повторный закуп товара с первичным lifecycle только по совпадению `productId`.
- [x] В одной транзакции сохранять поступление, изменение остатков, состояние связанного lifecycle и историю. Повторный запрос или одновременная приёмка из двух окон не должны удваивать остатки.
- [x] Если поступление уже существует, показывать его и следующий доступный шаг. Статус «Закрыта» сам по себе не подтверждает и не отменяет приёмку; фактические документы определяют возможность восстановления связи.
- [x] Для уже застрявших товаров подготовить адресное восстановление по подтверждённой приёмке: предварительный просмотр изменений, журнал, повторный безопасный запуск. Не начислять остаток повторно, не создавать новую заявку и не переписывать более поздние этапы товара.
- [x] При отсутствии однозначной приёмки показывать связанную заявку и конкретную проблему. Не добавлять кнопку бесконтрольного пропуска этапа.

Готовность: после приёмки через любой поддерживаемый вход соответствующие товары переходят на складской этап ровно один раз. Принятый товар восстанавливается и при закрытой заявке без новых движений по складу; непринятый не помечается принятым. Нулевая фактическая поставка не считается поступлением товара.

Проверка: одиночная и групповая заявки, окончательные расхождения вверх/вниз/ноль, повтор запроса, закрытая принятая заявка, отсутствие и неоднозначность связи. Основные места: `warehouseController.js`, `productLifecyclePurchaseController.js`, сервисы lifecycle-закупа и `procurementListController.js`.

## Этап 3. Чек при оплате

- [x] Проверить все входы оплаты: форма поставщика, форма заявки, действия при приёмке/расчёте. Файл относится к конкретному платежу, включая частичный, а не к заявке целиком или выбору «под реализацию» без движения денег.
- [x] Сохранить действующий контракт распределения платежей. Для формы заявки расширить текущий путь загрузкой либо использовать существующий платежный путь только после проверки эквивалентности расчётов; не создавать два платежа за одно действие.
- [x] Показывать имя выбранного файла, возможность убрать его до отправки, состояние загрузки и понятную ошибку. При ошибке выбранного файла не проводить платёж незаметно без чека.
- [x] Проверять тип и размер по согласованным ограничениям существующего загрузчика, поддержать востребованные изображения/PDF. Отображать сохранённый чек в истории платежей заявки и поставщика с учётом прав доступа.
- [x] При неуспешном сохранении очищать загруженный файл. Защитить отправку от двойного нажатия; после сетевой ошибки проверять результат перед повторной регистрацией платежа.

Готовность: полная и частичная оплата сохраняют один платёж с доступным чеком; оплата без файла продолжает работать, суммы долга совпадают с прежними правилами.

Проверка: платёж с файлом и без, запрещённый файл, ошибка сохранения, повторная отправка. Основные места: `PaymentModal.tsx`, `OrderDetails.tsx`, API оплаты, маршруты и контроллеры платежей/заявок. Новая миграция для `receiptUrl` не нужна, если существующая применена.

## Этап 4. Исправление заявок на разных стадиях

Замечания клиента: 3 и 4. Это один этап с двумя последовательными частями: сначала редактирование до приёмки, затем корректировка проведённых данных.

### Решение по правилам

Свободное удаление принятой или оплаченной заявки не вводить: оно скрывает основание остатков и долга. Вместо этого дать понятные действия по фактическому состоянию документов:

| Состояние | Доступное действие |
| --- | --- |
| Черновик без приёмок и платежей | Редактировать состав и цену, удалить ошибочную заявку |
| Отправлена/подтверждена/собирается/доставляется, приёмок нет | Исправить состав и цену; отменить заявку с причиной; если есть оплата, явно сохранить и урегулировать её как аванс/возврат |
| Есть приёмка | Изменить цену через корректировку; состав и количество менять через корректировку поступления или возврат по фактическому смыслу |
| Оплачена или закрыта | Те же корректировки по документам, с пересчётом расчётов; платежи и исходная история сохраняются |

### До приёмки

- [x] Проверять доступность действий по наличию приёмок, оплат и связей, а не только тексту статуса. Согласовать правила интерфейса и API; сохранить текущие роли, финансовые/складские корректировки первоначально разрешить администратору.
- [x] Разрешить удаление ошибочных строк и добавление других товаров до приёмки, включая связанные с lifecycle. Вместо снятия защиты в `orderItemSyncService` корректно освободить связи закупочного листа и первичного закупа в транзакции.
- [x] Удалённый из заявки товар, всё ещё требующий первичного закупа, должен снова быть доступен для закупки без дублей в листе и без фиктивного продвижения очереди. Новому товару не передавать историю старого.
- [x] Сохранять идентификаторы неизменённых строк. Проверить внешние связи перед удалением; пустую заявку предлагать отменить/удалить, а не игнорировать пустой массив товаров.
- [x] Показывать доступные действия и конкретные причины ограничений. Для отправленной заявки фиксировать изменения и возможность скачать обновлённую накладную; не отправлять её поставщику автоматически.

### После приёмки

- [x] Добавить действие «Корректировать» с обязательной причиной и предварительным отображением изменений. Фиксировать автора, дату и значения до/после. Сначала проверить пригодность существующей истории; если её недостаточно, добавить минимальную структуру корректировки и миграцию.
- [x] Исправление цены пересчитывает суммы строк и заявки, статус оплаты и сальдо поставщика. Фактические платежи сохраняются: снижение суммы ниже оплаченной создаёт видимую переплату/аванс, повышение создаёт остаток к оплате.
- [x] Изменение цены уже принятой партии не меняет количество на складе. Не перезаписывать автоматически текущую цену продажи, прайс поставщика и себестоимость всех последующих закупок.
- [x] Исправление количества или замена ошибочно оприходованного товара сохраняет исходный документ и проводит только разницу по складу и стоимости. Реальный возврат поставщику оформлять существующим возвратным процессом, а не маскировать удалением строки.
- [x] Если товар уже израсходован/перемещён и исправление нарушает доступный остаток или связанные документы, отклонять его с конкретной причиной. Не вводить отрицательные остатки и не переписывать дальнейшие движения молча.
- [x] При добавлении фактически полученного дополнительного товара предложить цену этого поставщика, при её отсутствии ручной ввод. Существующие принятые строки повторно на склад не начислять.
- [x] Обновлённые суммы и состав согласованно показывать в заявке, накладной, сверке, карточке поставщика и истории. Закрытую заявку не возвращать в начало цепочки ради изменения цены.
- [x] Отмену заявки с уже проведёнными документами не превращать в `isActive=false`. Сохранять доступ к документам и явно определять необходимые возвраты/корректировки и судьбу оплаты.

Готовность: администратор исправляет цену принятой и оплаченной заявки с историей и правильным сальдо; исправление состава даёт только необходимую разницу остатков. Удаление строки до приёмки не оставляет товар заблокированным в очереди. Ни одно действие не стирает реальные платежи и поступления.

Проверка: интеграционные сценарии цены вверх/вниз, полной/частичной оплаты и переплаты, замены связанной строки, дополнительного товара, недостаточного остатка, закрытой заявки и параллельных корректировок. Для этого этапа проверки шире из-за влияния на склад и деньги.

## Порядок выполнения и выпуск

1. Выполнять этапы 1 → 2 → 3 → 4. После каждого обновлять отметки в этом файле и выдавать короткий сценарий ручной проверки результата.
2. Перед изменениями перечитать актуальный код затронутых мест. Имена новых API/полей выбрать по фактической архитектуре; приведённые здесь решения не являются готовыми API-контрактами.
3. Не запускать полный аудит проекта на каждом этапе. Проверять изменённую логику и связанные пользовательские сценарии; этапы 2 и 4 обязательно проверять на реальной тестовой БД с транзакциями и повторными запросами.
4. Миграции и восстановление production-данных отделять от обычного запуска приложения: резервная копия, предварительная выборка затрагиваемых записей, согласованный запуск и проверка результата. Не менять неоднозначные записи автоматически.
5. В этом задании создаётся только roadmap. Код приложения, БД и production не изменять до начала реализации этапов.
