# 🔧 Исправление проблемы с дублированием рынков

## 📋 Описание проблемы

При попытке создать рынок с названием, которое уже использовалось в деактивированном рынке, возникала ошибка:

```
SequelizeUniqueConstraintError: повторяющееся значение ключа нарушает ограничение уникальности "markets_name_unique"
```

### Причина
Использовался обычный уникальный индекс `markets_name_unique`, который проверял уникальность названия среди **всех записей** (включая деактивированные с `is_active = false`).

## ✅ Решение

Реализован **паттерн Soft Delete с Partial Unique Index**:

### 1. Частичный уникальный индекс
Создан индекс `markets_name_active_unique`, который гарантирует уникальность названия **только среди активных** рынков:

```sql
CREATE UNIQUE INDEX markets_name_active_unique 
ON markets (name) 
WHERE is_active = true;
```

**Преимущества:**
- ✅ Можно иметь несколько деактивированных рынков с одинаковым названием
- ✅ Но только **один активный** рынок с каждым названием
- ✅ Позволяет "переиспользовать" названия после деактивации

### 2. Обновленная логика контроллера

**createMarket:**
- Проверяет наличие активного рынка с таким названием (регистронезависимо)
- Обрезает пробелы из названия

**updateMarket:**
- Проверяет конфликты с другими активными рынками
- Исключает текущий рынок из проверки

**deleteMarket:**
- По умолчанию делает мягкое удаление (is_active = false)
- Поддерживает физическое удаление через `?permanent=true`
- Проверяет наличие связанных активных поставщиков

**restoreMarket (новый):**
- Восстанавливает деактивированный рынок
- Проверяет конфликты с активными рынками перед восстановлением

## 🚀 Применение исправлений

### Шаг 1: Применить миграцию

```bash
cd server
npm run migrate
```

Применится миграция `20260125000000-remove-old-market-name-index.js`, которая:
1. Удалит старый индекс `markets_name_unique`
2. Проверит наличие частичного индекса `markets_name_active_unique`
3. Создаст его, если отсутствует

### Шаг 2: Очистить дубликаты (опционально)

Если в БД накопилось много неактивных дубликатов:

```bash
cd server
node scripts/cleanup-inactive-markets.js
```

Скрипт:
- Найдет все группы неактивных рынков с одинаковым названием
- Оставит самую новую запись
- Физически удалит остальные дубликаты

### Шаг 3: Перезапустить сервер

```bash
npm run start
```

## 📝 API Изменения

### Новый эндпоинт: Восстановление рынка

```http
POST /api/markets/:id/restore
Authorization: Bearer {admin_token}
```

**Пример ответа:**
```json
{
  "success": true,
  "message": "Рынок успешно восстановлен",
  "data": {
    "market": {
      "id": 3,
      "name": "Ялянь",
      "isActive": true,
      ...
    }
  }
}
```

**Ошибка при конфликте:**
```json
{
  "success": false,
  "message": "Невозможно восстановить. Активный рынок с названием \"Ялянь\" уже существует."
}
```

### Обновленный эндпоинт: Удаление

```http
DELETE /api/markets/:id?permanent=true
```

- Без параметра: мягкое удаление (is_active = false)
- С `?permanent=true`: физическое удаление из БД

### Сценарий 2: Восстановление

```bash

POST /api/markets
{
  "name": "Тестовый"
```

## 📊 Структура БД после исправления

```sql
-- Таблица markets
CREATE TABLE markets (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  is_active BOOLEAN DEFAULT true,
  ...
);

-- Частичный уникальный индекс (только для активных)
CREATE UNIQUE INDEX markets_name_active_unique 
ON markets (name) 
WHERE is_active = true;

-- Индекс для быстрого поиска по статусу
CREATE INDEX markets_is_active_idx ON markets (is_active);

-- Индекс для сортировки
CREATE INDEX markets_sort_order_idx ON markets (sort_order);
```

**Примеры допустимых данных:**

| id | name   | is_active |
|----|--------|-----------|
| 1  | Байсат | true      | ✅ OK
| 2  | Ялянь  | true      | ✅ OK
| 3  | Ялянь  | false     | ✅ OK (неактивный дубликат)
| 4  | Ялянь  | false     | ✅ OK (еще один неактивный)
| 5  | Ялянь  | true      | ❌ ОШИБКА! (два активных с одним именем)

## 🔒 Безопасность

- Все операции с рынками доступны только администраторам
- Физическое удаление блокируется при наличии связанных активных поставщиков
- Trim и регистронезависимое сравнение предотвращают "обход" через пробелы

## 📈 Производительность

- Частичный индекс занимает меньше места (индексируются только активные записи)
- Быстрый поиск по is_active через отдельный индекс
- Проверка уникальности на уровне БД (не требует запроса SELECT)
